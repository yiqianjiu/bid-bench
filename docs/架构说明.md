# 架构说明（bid-bench / 投标业务工作台）

> 版本 1.1.1。这是一份给「想改代码的人」看的文档，讲清每个文件管什么、一次点击在后端怎么走、AI 在哪些地方被调用、数据存在哪、要加功能该动哪。

---

## 一、总体结构

~~~
bid-bench/
├── app/
│   ├── server.mjs          HTTP 服务与全部路由（零框架，node:http）
│   ├── lib/                业务模块（22 个 .mjs）
│   ├── web/                前端单页（index.html + app.js + style.css，无构建）
│   └── config.example.json 配置模板（复制成 config.json 后填 Key）
├── scripts/                install.bat / start.bat / stop.bat
├── 数据/                    运行时生成：workbench.db + 文本/分析/制作/核查缓存
├── 项目/                    运行时生成：每个项目一个文件夹
├── 归档/                    项目关闭后归档到这里
└── docs/                    本文档等
~~~

设计约束（有意为之）：

1. **零依赖框架**：只有 4 个 npm 依赖（docx / mammoth / pdfjs-dist / pdf-to-img），其余全用 Node 内置能力（node:http、node:sqlite、node:zlib）。
2. **前端不打包**：app/web/app.js 是原生 JS 单页，改完刷新浏览器即生效。
3. **文件优先**：每个模块的中间结果都落 JSON 到项目目录，数据库只存项目索引；即使数据库坏了，项目文件夹里的东西还在。
4. **AI 可选**：没填 Key 时规则类功能（解析、生成框架、格式核查、行动清单）全都能用，只有「AI 分析 / 写正文 / 逐条核查 / 模拟评标」需要 Key。

## 三、一次请求怎么走

### 3.1 上传招标文件

~~~
浏览器 POST /api/projects/:id/files (multipart)
  → server.mjs 解析 multipart，落盘 项目/编号_项目名/01招标文件/
  → extract.mjs 抽文字（pdfjs）→ text.mjs 写缓存 数据/文本/<fileId>.json
  → files 表更新 pages / textChars / extracted
~~~

### 3.2 招标分析（耗时任务）

~~~
POST /api/projects/:id/analyze  → 建任务，返回 taskId（立即 202）
后台：ensureText → splitSegments(每段 ≤N 页) → 分段并发调 AI
     → 14 个板块各自归并（merge 阶段）→ 数据/分析/<pid>.json
GET /api/tasks/:taskId 轮询 {state: running|done|error, message}
~~~

要点：分析结果一旦落盘，后面写正文、核查、递交清单全都读它，不会重复花钱分析。

### 3.3 生成标书正文

~~~
POST /api/projects/:id/draft/:doc/chapter/:cid  {action:"generate"}
  → draft.mjs generateChapter()
    → clauseKeysFor(docKey,title) 选板块（技术类→tech/deliver/business…）
    → 按相关度排序、字数封顶 24000，再恢复招标原文顺序
    → 若本章 role 为 tech/biz：先取已确认的专家画像（profile.mjs），
      没有就先返回 needProfile，前端弹窗确认后才继续
    → prompt.mjs draftUserPrompt() 拼提示词（叠加专家身份 + 知识库参考）
      → callText(temperature 0.5)；重要章节字数低于下限时自动再要一版
    → checkCoverage() 算「覆盖 N/M 条」→ 写回 制作/<pid>.json
~~~

### 3.4 文件核查

~~~
POST /api/projects/:id/check  → 任务
  → listSources()：列出候选文件，标 final（你上传的最终版）/ export（草稿）/ other
  → 只核查 final（无 final 则全部）
  → checkOneDoc()：docx→pdf（Word COM）→ 抽文字 + 每页图片数
  → ruleCheck()：空白页 / 页码 / 封面要素 / 占位 / 日期 / 项目名称编号
  → aiRequirementCheck()：328 条要求分批比（每批 ≤55 条），每条给 2/1/0 + 证据 + 页码
  → aiDeepScore()：逐个评分项单独评分，先找索引表，没有就全文按页检索
  → 数据/核查/<pid>.json
GET /api/check-tasks/:taskId 轮询（核查任务和分析的 /api/tasks 是两套接口）
~~~

### 3.5 导出 Word

四个 export*.mjs 都用 docx 库，共用两套排版约定：表格 FIXED 布局 + dxa 列宽（按列内容权重分配，每列 ≥600dxa）；表格行 cantSplit（不跨页断开）。导出后可选走 Word COM 转 PDF 检查排版。

## 四、AI 调用策略

| 场景 | 模型能力 | 输入 | 输出 |
|---|---|---|---|
| 分析 13 板块 | 文本 | 分段原文（带页码） | JSON 数组（板块内条目） |
| 扫描件识别 | 视觉 | 页面 PNG（base64） | 纯文字 |
| 写章节正文 | 文本 | 条款原文（带页码）+ 评分标准 + 本章要求 | 纯正文，无 markdown |
| 逐条核查 | 文本 | 要求清单 + 相关页原文 | JSON：n / s / e（证据）/ note |
| 模拟评标 | 文本 | 单个评分项 + 索引页 + 相关页 | JSON：breakdown / lost / risk / improve |

共同约定：

- 只用招标文件原文当依据，禁止通用模板（提示词里写了最高原则）。
- 长文档不整份送：先按「页级 bigram 相关度」挑页（pickPages），并保留 mustPages（索引页、报价页）。
- 被省略的页数会回传（omittedPages），界面上明确提示「有 N 页没放进本次范围，请人工确认」。
- 提示词要求 JSON 输出时不使用 response_format，而是从回复里抠第一个 {...} 或 [...] 解析。

## 七、已知边界

1. **无本地 OCR**：扫描件靠 DeepSeek 视觉逐页识别，页数多时较慢且要花钱；纯图片 PDF 的页数、字数统计以识别结果为准。
2. **docx→PDF 依赖 Windows + 安装 Microsoft Word**（用 COM）；没装 Word 的机器上，核查中的 PDF 相关步骤会失败并给出提示。
3. **AI 结论需人工复核**：逐条核查的「部分响应」大量来自电子文件无法体现的事项（装订、密封、现场递交、CA 证书），设计上就是提醒人工确认，不是判定。
4. **超长标书只核对相关页**：161 页的标书不会整份送 AI，而是在页级检索后取相关页；被跳过的页会在界面上写明。
5. **知识库不是向量检索**：按采购方式 + 技术关键词重合度打分，几十个项目内够用，项目数上百后建议换向量库。
6. **中文语境**：板块、提示词、评分逻辑都按中国大陆政府采购/招标习惯写。

## 八、开发与调试

~~~bash
# 直接跑（开发模式，改前端刷新即可，改后端要重启）
node app/server.mjs

# 指定数据根目录（不污染仓库）
TWB_ROOT=/tmp/twb-test node app/server.mjs

# 检查接口是否活着
curl http://127.0.0.1:7830/api/health
~~~

常见故障：

- 7830 被占用：改 app/config.json 的 port（前端会跟着 /api/health 的返回走）。
- Word 转换卡住：任务管理器结束 WINWORD.exe 后重试（脚本以只读方式打开、不保存）。
- 分析结果是空：先看数据/文本/<fileId>.json 有没有 pages；没有就是抽取失败（PDF 加密或非标准格式）。
